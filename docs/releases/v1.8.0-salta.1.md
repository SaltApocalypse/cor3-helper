## Highlights

### Mailbox Auto-Claim (new game reward flow)

- **Mercenary expeditions**: after paying via `open.container`, rewards are delivered to the stash mailbox instead of directly to the stash. The helper now claims every matching `EXPEDITION` mail message automatically, then refreshes mercenaries and dispatches the next expedition.
- **Personal drone**: successful missions deliver loot directly to the mailbox. The helper claims matching `DRONE_MISSION` messages, clears the completion state, and dispatches the next mission.
- Claims all pending expedition/drone mailbox messages when the corresponding automation is enabled.
- Capacity-aware: checks warehouse cells before claiming, can auto-sell the cheapest items, and falls back to `mail claim.item` with computed free rectangles when `claim.all` cannot place a fragmented reward.
- Mailbox claiming pauses while warehouse sorting is running.

### Warehouse Grid & Sorting

- Supports the new 12-wide warehouse grid with item footprints (`width` × `height`, optional rotation).
- **Default Sort**: rarity first, then item name; row-major first-fit packing, rotating items when needed.
- **Horizontal Sort**: each item type gets its own row band; copies fill the band left-to-right and wrap downward inside that band.
- Layouts are fully precomputed before any movement. If the required rows exceed the warehouse capacity, sorting is rejected.
- Already-correct items are skipped. The in-game sorting table is used only for items blocking a target position.
- Sorting is serialized (one `stash move.item` at a time), shows progress, and warns not to refresh or close the page.
- On failure, the sorter stops and attempts to return items still parked in the sorting table to their original cells.

### Inventory Improvements

- Merged duplicate item types into one card with an `xN` quantity badge.
- Added **SUPERRARE** rarity.
- Final rarity order: `QUEST > LEGENDARY > EPIC > SUPERRARE > RARE > COMMON`.
- Batch-sell rarity filter now includes SUPERRARE.
- `QUEST` is a value of the game's `tier` field (quest items), not a separate tag; it is kept first per the fork's configured order.

### Stability Fixes

- “Already in progress” / busy errors are treated as transient:
  - Drone automation no longer pauses on these errors.
  - Expedition launch/setup errors no longer get mistaken for a successful launch.
  - `open.container` payments retry with backoff when the game is still processing another action.
- Added drone action locking so repair/launch/claim requests are not duplicated before the previous action is confirmed.

### Documentation

- Added `docs/cor3-ws-events.md` with the live mailbox, stash grid, sorting table, expedition, drone, and gameplay event shapes, internal bridge messages, storage keys, and error-handling rules.

## Installation

1. Download `cor3-helper-v1.8.0-salta.1.zip` from this release.
2. Extract the archive to a folder.
3. Open `chrome://extensions/` and enable **Developer mode**.
4. Click **Load unpacked** and select the extracted folder (the one containing `manifest.json`).
5. Open [cor3.gg](https://cor3.gg) and log in.
6. Open the extension popup.

## Game Version Tracking

`versions.json` tracks the live game's web/system/patch versions. The fork serves its own copy, mirrored from upstream and refreshable with:

```bash
npm run sync-versions
```

Sync is fully manual (`npm run sync-versions`). The release workflow warns if `versions.json` is stale before building.

To read the live values, open the game with the extension loaded and check the popup version footer (`Web`, `System`, `Patch`), or run in the popup DevTools console:

```js
chrome.storage.local.get(['webVersion', 'systemVersion', 'patchVersion'])
```

## Notes

- Warehouse sorting can take a long time because every move is a server round-trip. Do not refresh or close the page while sorting.
- The sorting table must be empty before starting a sort; close/reopen the warehouse window to return any items left there.
- Auto-claim and auto-sell are paused while sorting.
- Build verified with `npm run build`; layout/move planning was also validated offline against the captured warehouse data.
